# Alphonse architecture and interfaces

This guide reviews the pinned `ALPHONSE_NEW_V2` snapshot. It follows selected manager, launch and controller-interface ranges; it is not an exhaustive architecture audit. Source mismatches are reported as open issues. No ROS launch, build, simulator, serial operation or robot action was executed.

## Startup and configuration ownership

The launch file selects the manager's `offset.yaml`, `OP3.robot` and `dxl_init_OP3.yaml`, and points `OP3_ACTION_FILE` at `op3_action_module/data/ALPHONSE.bin`. It exposes separate `device_name` and `sub_controller_device` launch arguments, with a servo-bus FTDI by-id path and a separate OpenCR by-id path as defaults. The comments describe an Alphonse-specific bus workaround; this review does not verify the physical board condition or transfer those paths to another robot. [source/src/ROBOTIS-OP3/op3_manager/launch/op3_manager.launch.py:L13-L50](https://github.com/ProgramBascorro/motion_webots/blob/adacde8f6e01e6439d170fb6bce025acc051bfa3/src/ROBOTIS-OP3/op3_manager/launch/op3_manager.launch.py#L13-L50)

The manager creates the ROS node `op3_manager` and obtains the `RobotisController` singleton. It declares and reads file paths, serial-device names and baud rate. An empty `sub_controller_device` falls back to `device_name`; that compatibility path should not be mistaken for proof that Alphonse can use a single serial port. [source/src/ROBOTIS-OP3/op3_manager/src/op3_manager.cpp:L248-L273](https://github.com/ProgramBascorro/motion_webots/blob/adacde8f6e01e6439d170fb6bce025acc051bfa3/src/ROBOTIS-OP3/op3_manager/src/op3_manager.cpp#L248-L273)

## Initialization path

When its `simulation` parameter is false, the manager opens the sub-controller port and attempts power and LED writes. It then opens the servo-bus port and waits for a Dynamixel response, with a source-defined timeout. These are active hardware operations in the implementation, not a read-only startup inspection. [source/src/ROBOTIS-OP3/op3_manager/src/op3_manager.cpp:L282-L365](https://github.com/ProgramBascorro/motion_webots/blob/adacde8f6e01e6439d170fb6bce025acc051bfa3/src/ROBOTIS-OP3/op3_manager/src/op3_manager.cpp#L282-L365)

An empty robot-file path or failed controller initialization returns an error. Otherwise, the manager optionally loads offsets, registers the OpenCR sensor module, registers action/base/head/walking/direct-control/online-walking/tuning motion modules, and starts the controller timer. Registration does not establish which module controls each joint later. [source/src/ROBOTIS-OP3/op3_manager/src/op3_manager.cpp:L378-L410](https://github.com/ProgramBascorro/motion_webots/blob/adacde8f6e01e6439d170fb6bce025acc051bfa3/src/ROBOTIS-OP3/op3_manager/src/op3_manager.cpp#L378-L410)

The launch file declares an integer `boot_init_page` default of 2, with comments describing positive, zero and negative modes; it converts the launch argument to an integer parameter. The reviewed manager range also declares and reads that parameter. This records the configuration contract only; actual pose execution and action-file contents were not validated here. Do not copy page meanings or motion data between robots. [source/src/ROBOTIS-OP3/op3_manager/launch/op3_manager.launch.py:L41-L77](https://github.com/ProgramBascorro/motion_webots/blob/adacde8f6e01e6439d170fb6bce025acc051bfa3/src/ROBOTIS-OP3/op3_manager/launch/op3_manager.launch.py#L41-L77) [source/src/ROBOTIS-OP3/op3_manager/src/op3_manager.cpp:L414-L435](https://github.com/ProgramBascorro/motion_webots/blob/adacde8f6e01e6439d170fb6bce025acc051bfa3/src/ROBOTIS-OP3/op3_manager/src/op3_manager.cpp#L414-L435)

## ROS and controller interfaces

The manager subscribes to OpenCR button and Dynamixel-torque topics. It creates publishers for initial pose, ball-tracker commands, control-module selection and action-page numbers. Those publisher declarations do not by themselves establish that a subscriber is present or that a physical action succeeds. [source/src/ROBOTIS-OP3/op3_manager/src/op3_manager.cpp:L275-L280](https://github.com/ProgramBascorro/motion_webots/blob/adacde8f6e01e6439d170fb6bce025acc051bfa3/src/ROBOTIS-OP3/op3_manager/src/op3_manager.cpp#L275-L280)

`RobotisController` is declared as both a singleton and an `rclcpp::Node`. Its header exposes initialization, module registration, timer control, control-module selection, offset loading, joint/control-table callbacks and related services. Thread members are declared, but their scheduling and lifecycle require implementation-level review. [source/src/ROBOTIS-Framework/robotis_controller/include/robotis_controller/robotis_controller.h:L60-L75](https://github.com/ProgramBascorro/motion_webots/blob/adacde8f6e01e6439d170fb6bce025acc051bfa3/src/ROBOTIS-Framework/robotis_controller/include/robotis_controller/robotis_controller.h#L60-L75) [source/src/ROBOTIS-Framework/robotis_controller/include/robotis_controller/robotis_controller.h:L125-L165](https://github.com/ProgramBascorro/motion_webots/blob/adacde8f6e01e6439d170fb6bce025acc051bfa3/src/ROBOTIS-Framework/robotis_controller/include/robotis_controller/robotis_controller.h#L125-L165)

The sampled health-handler range returns a successful response with a `skipped`/`simulation` payload when simulation is enabled. That path is not evidence that any hardware responded. [source/src/ROBOTIS-OP3/op3_manager/src/op3_manager.cpp:L480-L495](https://github.com/ProgramBascorro/motion_webots/blob/adacde8f6e01e6439d170fb6bce025acc051bfa3/src/ROBOTIS-OP3/op3_manager/src/op3_manager.cpp#L480-L495)

## Source mismatches and remaining checks

- **Simulation naming:** launch supplies `gazebo` and `gazebo_robot_name`, while the manager reads `simulation` and, in its simulation branch, `simulation_robot_name`. No mapping between those names was established in the inspected ranges. Verify the effective parameters before relying on a simulation-only startup. [source/src/ROBOTIS-OP3/op3_manager/launch/op3_manager.launch.py:L64-L77](https://github.com/ProgramBascorro/motion_webots/blob/adacde8f6e01e6439d170fb6bce025acc051bfa3/src/ROBOTIS-OP3/op3_manager/launch/op3_manager.launch.py#L64-L77) [source/src/ROBOTIS-OP3/op3_manager/src/op3_manager.cpp:L282-L284](https://github.com/ProgramBascorro/motion_webots/blob/adacde8f6e01e6439d170fb6bce025acc051bfa3/src/ROBOTIS-OP3/op3_manager/src/op3_manager.cpp#L282-L284) [source/src/ROBOTIS-OP3/op3_manager/src/op3_manager.cpp:L367-L375](https://github.com/ProgramBascorro/motion_webots/blob/adacde8f6e01e6439d170fb6bce025acc051bfa3/src/ROBOTIS-OP3/op3_manager/src/op3_manager.cpp#L367-L375)
- **Documentation age:** the controller-message README contains Kinetic/Melodic-era references and upstream links. It does not establish which ROS 2 message packages are installed or built in this deployment. [source/src/ROBOTIS-Framework-msgs/README.md:L1-L15](https://github.com/ProgramBascorro/motion_webots/blob/adacde8f6e01e6439d170fb6bce025acc051bfa3/src/ROBOTIS-Framework-msgs/README.md#L1-L15)
- Serial identities, calibration values, action contents, remaining health logic and full motion-module behavior still need robot-specific verification.
